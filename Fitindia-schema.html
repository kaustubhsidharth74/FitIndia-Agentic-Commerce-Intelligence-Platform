SEC-01

What It Does

FitIndia is a full-stack AI commerce demonstration — Express 4.18 backend, Next.js 14 frontend, Razorpay payment infrastructure, and five autonomous agents powered by Groq's llama-3.3-70b-versatile. Every agent action writes a reason + metadata to audit_log before any Razorpay call is made.

Three Agent-Driven Flows

CHECKOUT

Conversational Purchase

The Checkout Agent (Groq llama-3.3) runs a tool-calling agentic loop — search_catalog, create_payment_link, check_payment_status — responding to natural-language chat. A mock fallback handles keyword matching when MOCK_AI=true.

  • Webhook verifies HMAC-SHA256 signature on Razorpay callbacks
  • Buyer Bot agent (customer type=bot) auto-purchases from catalog via API
  • Cart endpoint supports multi-item checkout in a single Razorpay payment link
RECOVERY

Failure & Cart Recovery

When a payment fails, the Retry Agent triggers, checks retry_enabled guardrail, creates a fresh payment link, and logs a merchant_alert if retries are exhausted. The Campaign Agent scans abandoned carts (pending orders) and sends AI-personalized recovery messages via Groq.

  • Max 3 reminders per order — enforced by max_reminders_per_order guardrail
  • Campaign uses compose_campaign_message tool to generate SMS-friendly copy
  • Conversions tracked as campaign_converted audit entries with amount
PROTECT

Fraud Detection

A deterministic fraud scorer (fraudScorer.js) assigns risk scores based on order velocity, amount thresholds, bot customer type, and status patterns. Suspicious orders are surfaced on the Fraud page with block/approve actions. No LLM involved — pure code-layer logic.

  • Risk levels: low / medium / high
  • Blocked orders set status to held, logged to audit trail
  • Auto-approve threshold: ₹5,000 (max_auto_approve_inr)

SEC-02

Agent Ecosystem

Five autonomous agents, each in its own file under backend/agents/. All agents write to audit_log before taking action, read guardrails before spending money, and degrade gracefully to mock/fallback when API keys are absent.

The Five Agents

CHECKOUT

checkout_agent — checkoutAgent.js

Conversational shopping assistant. Accepts a message history array and customer ID, runs a Groq agentic loop with 3 tools, returns a reply string and optional Razorpay payment link URL.

  • Model: llama-3.3-70b-versatile via Groq SDK
  • Tools: search_catalog, create_payment_link, check_payment_status
  • Loop: max 5 iterations; exits on finish_reason=stop
  • Mock: keyword-matching fallback when MOCK_AI=true
BUYER BOT

buyer_agent — buyerAgent.js

Automated AI buyer (bot customer, type=bot, id=4). Reads the machine-readable catalog at GET /api/catalog, selects products by goal, posts to POST /api/buy and creates Razorpay payment links autonomously.

  • Input: botCustomerId, goal, optional targetProductName, quantity
  • Demonstrates agent-to-agent commerce: another agent can invoke the buyer
  • All purchases logged to audit trail as catalog_buy
UPSELL

upsell_agent — upsellAgent.js

Analyzes a customer's recent purchase history, proposes a complementary product with a discount offer. Enforces max_upsell_discount_pct=30 guardrail — no offer exceeds 30% off regardless of LLM suggestion.

  • Triggered via POST /api/agent/upsell with customer_id
  • Discount capped at 30% — code-layer guard, not prompt instruction
  • Writes action_type=upsell to audit_log before payment link creation
CAMPAIGN

campaign_agent — campaignAgent.js

Abandoned cart recovery orchestrator. Scans pending orders older than CAMPAIGN_MIN_AGE_HOURS, generates personalized recovery messages using Groq's compose_campaign_message tool, creates fresh payment links, logs reminders to audit trail.

  • Model: llama-3.3-70b-versatile via Groq SDK
  • Tool: compose_campaign_message — tone: friendly/urgent/final based on attempt
  • Guardrail: max 3 reminders per order (max_reminders_per_order)
  • Fallback: 3 hardcoded templates when Groq key absent
RETRY

retry_agent — retryAgent.js

Payment failure handler. When called after payment.failed webhook, checks retry_enabled guardrail, creates a new Razorpay payment link, updates the order, logs the retry attempt. Sends merchant_alert if retries are exhausted.

  • Triggered by POST /api/agent/retry or POST /api/agent/simulate-failure
  • Guardrail: retry_enabled=true must be set or agent refuses to act
  • Also exports simulatePaymentFailure for demo/testing

SEC-04

Data Flow

The checkout agent runs an agentic tool-calling loop — it queries the catalog, confirms the product with the customer, creates a Razorpay payment link, and waits for the webhook to confirm payment. Every step is logged to audit_log.

Checkout Agent — Agentic Loop (6 steps)

01 — TRIGGER
User Chat
Customer types intent in /chat page. Next.js ChatBox sends full message history + customer_id to Express.
POST /api/agent/chat
02 — AGENT
Checkout Agent
Groq llama-3.3-70b-versatile receives messages. Enters tool-calling loop — max 5 iterations. Exits on finish_reason=stop.
Groq SDK
03 — TOOL
search_catalog
Agent calls tool. Raw SQL query on products table. Returns name, price, stock. Agent reads matches and confirms product with user.
SQLite → products
04 — TOOL
create_payment_link
Agent calls Razorpay SDK createPaymentLink() with amount in paise, customer email, order notes. DB order inserted with status=pending.
Razorpay SDK
05 — PAYMENT
Customer Pays
Agent replies with short_url. Customer clicks link, pays on Razorpay page. Razorpay fires payment_link.paid webhook to Express.
POST /api/webhook
06 — RESOLVED
Order Confirmed
HMAC-SHA256 verified. Order status → paid, razorpay_payment_id stored. Audit entry: agent=webhook, result=success.
audit_log: success

Buyer Bot Agent — Automated Purchase (5 steps)

01 — TRIGGER
Bot Activated
Buyer agent triggered via POST /api/agent/buyer. Uses bot customer id=4 (type=bot, email: fitbot@fitindia.ai).
botCustomerId=4
02 — CATALOG
Fetch Products
GET /api/catalog returns all products with price, stock, and agent_instructions field — machine-readable format for AI agents.
GET /api/catalog
03 — SELECT
Product Selection
Agent filters by goal or targetProductName. Validates stock > 0. Falls back to first in-stock item if target not found.
goal-based filter
04 — ORDER
Buy + Link
POST /api/buy → catalog.js creates DB order, calculates total_paise. Razorpay SDK createPaymentLink() returns short_url.
Razorpay SDK
05 — AUDIT
Trail Written
Audit entry written: agent=buyer_agent, action_type=catalog_buy, result=pending. Returns db_order_id + payment_link to caller.
audit_log: pending

3-Stage Request Lifecycle

01

Order Created (pending)

DB order inserted with status='pending'. Razorpay payment link created (real or mock). Link URL saved back to order row. Audit entry with result='pending' written.

02

Payment Attempted

Customer clicks link, pays via Razorpay. Razorpay sends payment_link.paid webhook to POST /api/webhook. HMAC-SHA256 signature verified against RAZORPAY_WEBHOOK_SECRET.

03

Order Resolved

Order status updated to paid, razorpay_payment_id stored. Audit entry inserted with result='success'. Revenue accumulates in dashboard stats via GET /api/agent/stats.

SEC-05

Failure Handling

Two agents handle the post-failure lifecycle. The Retry Agent creates a fresh payment link when a payment fails. The Campaign Agent recovers abandoned carts with AI-personalized messages — bounded by guardrails to prevent spam.

Payment Failure → Retry → Campaign Recovery

flowchart TD
  PF([payment.failed\nwebhook event]) --> RA[retry_agent\nretryAgent.js]
  RA -->|check guardrail| GR{retry_enabled\n= true?}
  GR -->|false| MA1[merchant_alert\naudit_log]
  GR -->|true| RL[Create new\nRazorpay payment link]
  RL -->|UPDATE orders| DB[(SQLite)]
  RL -->|audit payment_retry| AL[audit_log\nresult=pending]
  AL --> OUT{Customer\nresponds?}
  OUT -->|pays| PAID([Order paid\nstatus=success])
  OUT -->|ignores| CA[campaign_agent\nGroq llama-3.3]
  CA -->|count reminders| REM{reminders\n< max 3?}
  REM -->|yes| MSG[compose_campaign_message\ntool call — tone: friendly/urgent/final]
  MSG -->|fresh link| CA2[audit campaign\norder reminder]
  REM -->|maxed out| MA2[merchant_alert\neudit_log]

SEC-06

Guardrails

Four hard limits enforced in backend/config/guardrails.js. These are code-layer checks, not prompt instructions — agents query guardrails.get() and the JavaScript enforces the boundary before calling any external API. Readable and patchable at runtime via POST /api/agent/guardrails.

UPSELL CAP

max_upsell_discount_pct = 30

No upsell offer may exceed 30% off the product price. The Upsell Agent reads this before calculating the discount — even if an LLM suggests higher, the code caps it. Default: 30.

AUTO-APPROVE

max_auto_approve_inr = 5000

Orders at or below ₹5,000 may be automatically handled by agents without merchant intervention. Orders above this threshold surface a merchant_alert for human review. Default: 5000 (paise: 500000).

REMINDERS

max_reminders_per_order = 3

The Campaign Agent counts how many times a specific order has already received a recovery message (by querying audit_log WHERE action_type='campaign' AND order_id=?). If the count hits 3, it stops — preventing spam. Default: 3.

RETRY GATE

retry_enabled = true

Boolean kill-switch for the Retry Agent. If set to false, the agent refuses to create new payment links after failures and immediately logs a merchant_alert instead. Default: true.

Runtime Config API

# Read current guardrail values GET /api/agent/guardrails → { max_upsell_discount_pct: 30, max_auto_approve_inr: 5000, max_reminders_per_order: 3, retry_enabled: true } # Patch at runtime (no server restart required) POST /api/agent/guardrails { "max_upsell_discount_pct": 20, "retry_enabled": false } # Toggle mock flags at runtime POST /api/config { "mock_razorpay": true, "mock_ai": true }

SEC-09

User Journey

A customer's lifecycle from first visit to paid order — showing which agents activate and which audit entries are written at each stage.

STEP 01

Browse Catalog

Customer visits /catalog page. Next.js calls GET /api/catalog to render the product grid. ProductCard components show price in ₹ and stock status. No agent involvement — pure data read.

STEP 02

Chat-Driven Purchase

Customer types intent in ChatBox on /chat page. Message history sent to POST /api/agent/chat. Checkout Agent runs Groq agentic loop — calls search_catalog tool, confirms product, calls create_payment_link tool. Audit entry written: agent=checkout_agent, action_type=checkout, result=pending.

STEP 03

Payment Initiated

Customer clicks the Razorpay payment link returned by the agent. Razorpay hosts the payment page. Order remains in status=pending until webhook fires. Developer can monitor via GET /api/razorpay/orders or use POST /api/razorpay/sync-status to poll for localhost.

STEP 04A

Payment Succeeds — Webhook Fires

Razorpay sends payment_link.paid to POST /api/webhook. Signature verified. Order updated to status=paid, razorpay_payment_id stored. Audit entry: agent=webhook, action_type=payment, result=success. Dashboard stats update instantly.

STEP 04B

Payment Fails — Retry Agent Activates

payment.failed webhook updates order to status=failed. Demo page can trigger this via POST /api/agent/simulate-failure. Retry Agent checks retry_enabled guardrail, creates fresh payment link, logs payment_retry to audit. Merchant alert raised if retry also fails.

STEP 05

Abandoned Cart Recovery

If customer abandons the checkout, their order stays in status=pending. Campaign Agent (triggered manually or on schedule) scans pending orders older than CAMPAIGN_MIN_AGE_HOURS. Groq generates a personalized 160-char recovery message — tone evolves: friendly → urgent → final. Max 3 reminders enforced by guardrail.

STEP 06

Upsell Offer

After any successful paid order, merchant can trigger POST /api/agent/upsell with the customer's ID. Upsell Agent analyzes purchase history, proposes a complementary product with a discount. Offer capped at 30% off by max_upsell_discount_pct guardrail. Logged as action_type=upsell.
